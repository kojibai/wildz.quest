# Wallet peer trade implementation boundary

> This audit records the stock 128 boundary before implementation. The coordinated additive v128 implementation now exists in source; see [the implementation and rollout record](../../developers/native-wallet-rollout.md). Production rollout and live qualification remain outstanding.

Date: 2026-10-09. Source inspected: installed `@receiz/sdk` 128.0.0 and the Wildz adapters. This is a source audit; no live trade, funds movement, or custody transition was executed.

## Outcome

The existing private one-use creature offer workflow uses the historical bearer instrument protocol. Stock SDK128 requires an explicitly configured compatibility host for that protocol; the default client does not qualify it. When that historical source is actually configured, offers bind a native recipient through a verified account resolver or retain the existing private open-bearer path's application target-handle check. Named resource packages additionally require verified native recipient binding and conditional resource custody APIs, which the stock installed client does not expose. Native Φ execution needs a prepared transition source; the default runtime rejects a transfer review before issuing proofs or sessions when that source is absent. The current adapters do not expose a verified execution source that atomically exchanges Φ and native creature or resource ownership. Do not expose a Trade confirmation button until that source is available and qualified. Sequential sends or separately claimable gift instruments cannot satisfy a bilateral trade.

Direct-send recovery also has a specific limit: `app/api/wilds/cards/transfers/route.ts` issues before publishing its private offer, with no durable client command/plan lookup. A lost issue response can leave its transfer ID unknown. Inbox/thread reads can include locally admitted, unpublished messages and therefore cannot prove private delivery. The wallet preserves a per-owner source lock across reload for that uncertain creature; it must report the missing canonical offer/publication recovery instead of promising automatic completion or issuing another instrument. Confirmed published sends and idempotent resource package retries have separate recovery paths. This limitation is not evidence that a bilateral trade can commit.

## What the installed SDK supports

- `node_modules/@receiz/sdk/dist/v124Execution.js:155` accepts settlement/reserve value intents without imposing an expected domain ID. Its ownership adapter at line 253 requires a canonical `receiz.world.transaction.v122` whose commands are `subject.ownership.transfer`, bound to that transaction's world. Therefore a shared world can pass planning checks; mixed native value and ownership domains are not inherently the only blocker. The planner at line 340 checks exact participant heads and promises zero writes on failure. It does not supply the ownership reducer.
- `node_modules/@receiz/sdk/dist/v124Execution.js:569` requires `stagePrepared` with a pinned-verified portable transition set. `execute` at line 580 rejects a handle that lacks that source at line 585 with `V124_EXECUTION_TRANSITION_SOURCE_REQUIRED`. An operation plan or a constructed ownership event is insufficient.
- `node_modules/@receiz/sdk/dist/v124PortableAuthority.js:279` verifies exact predecessor/candidate seals, current identity evidence and signed capabilities, reconstructing each actual append. The transition set is subordinate to those artifacts. `v124PortableAuthority.d.ts:244` describes recovery as packaging already committed transitions with retained SDK custody, not granting arbitrary pre-execution custody changes.
- `node_modules/@receiz/sdk/dist/v124WorldComposite.js:216` requires execution events and accepted world/subject heads, and line 282 binds a receipt. This is an execution projection, not a substitute for an unexecuted custody source.

## Missing custody bridge

The modern `ownership.claimBearerAsset` path is distinct from the historical instrument protocol. Its stock SDK/server checks require verified `portable_asset` continuity (`packages/receiz-sdk/src/index.ts:4424`, `app/lib/sdk/bearerOwnershipClaim.server.ts:183` in the primary Receiz source). Wildz's sealed PNG exports carry `native_record_seal` continuity. Calling that method with those PNG artifacts therefore does not supply a working native creature gift. A source migration or qualified native successor adapter must preserve the original sealed payload and actual custody/history instead of relabeling its carrier. Current resource packages also need retained native package/member sources; canonical inventory JSON alone does not supply that custody.

`node_modules/@receiz/sdk/dist/livingSubjectRuntime.js:1026` stages world commands but preserves both `ownershipHead` and `currentOwnerReceizId` at lines 1061–1062. The supported bearer claim path starts at line 1625, changes those native ownership fields at line 1729, consumes its instrument and emits its ownership event in `world:ownership` at line 1737. Merely naming a world command `subject.ownership.transfer` does not perform that claim.

`node_modules/@receiz/sdk/dist/livingSubjects.d.ts:581` defines recipient, expiry, acceptance and inventory/memory policy for bearer instruments. It has no reciprocal consideration, exact trade plan or conditional bundle-commit field. The current Wildz paths (`src/lib/receiz/wilds-card-transfer.ts`, `wilds-resource-package.ts`, `wilds-resource-package-server.ts`) issue and claim these instruments independently. The adapter exposes planning, prepared execution and bearer claims separately in `src/lib/receiz/adapter.ts`; it exposes no aggregate bearer-claim/value executor. Subject-source preparation in `v124ReplayProofObject.js:2450` prepares unsealed source bytes and explicitly returns no subject authority. It cannot be used to forge a changed owner.

## Supported native source preparation

`src/lib/receiz/wilds-wallet-execution-source-member.ts` implements the existing SDK128 member recipe. It opens predecessor and identity bytes under pinned roots, admits their original seals, checks the exact native participant history head and owner, and verifies the signed issuer key-state snapshot. It uses `planArtifactAppend`, signs a capability restricted to that plan, commit domain, resource and SDK-derived effects, verifies the capability, then calls `sealArtifactTransitionCandidate`. The native sealer forwards the entire SDK-generated successor byte sequence to `client.assets.createProofObject`, with a plan-bound idempotency key. Preparation returns uncommitted member transport; combining members reopens every candidate and invokes the SDK's pinned transition-set verifier. Test-root admissions can exercise mechanical preparation but cannot pass this production set verifier.

The deployment source port in `wilds-wallet-v124-runtime.ts` forwards the exact supplied portable transition set to `stagePreparedExecutionV124`; it never calls plan-only staging. Absent source support makes Settlement and Reserve unavailable and returns `SOURCE_UNAVAILABLE` for older sealed attempts before mutation. Committed projections take the recipient username from the decrypted, actor-bound attempt.

The native edge plan API is `client.value.edge.planSettlement` / `planReserve`, documented in `node_modules/@receiz/sdk/docs/v125-edge-value-transfers.md`. It requires the genuine sender source proof and current value/history head, plus the receiver's genuine subject and current history head. Each participant must supply its actual sealed predecessor, identity evidence, current revocation evidence and held-key signature, or a complete already signed exact member. The recipient alias or a projected balance cannot supply these inputs. The current locator-bound plan derives a synthetic unconsumed-locator head; it cannot be converted into an admitted recipient artifact history by inventing a predecessor. A source bridge must use a supported native recipient-source path before qualifying execution.

`projectReceizIdentityAccount` verifies the signed portable account snapshot and exposes its carried wallet state; it does not manufacture a spendable source head. `namespaceReducer.js:250` supports provenance, profile showcase and economy showcase appends; a provenance append preserves the settlement and wallet namespace bytes. The source bridge must therefore preserve and admit the native value origin and exact settlement evidence. It must not reinterpret a display balance, synthetic test proof, independently sealed event or delegated Connect transfer as completed native Settlement/Reserve execution.

### Reproducing the native diagnostic recipe

The primary SDK fixture implementation is `packages/receiz-sdk/test/helpers/v112TransitionAuthority.ts:createCurrentTransitionPlanningAuthority`; native test sealing is in `test/helpers/canonicalArtifact.ts`, and member construction is exercised in `test/v124PortableAuthority.test.ts:305–450`. Run that SDK test with its repository's TypeScript test loader. These fixtures use freshly generated synthetic keys and explicit test roots and confer no production authority.

For the Wildz preparation check, use the installed SDK instance consistently for those helpers and for `prepareWildsWalletExecutionSourceMemberFromAdmissions`; separate SDK module instances have separate custody WeakSets. Start with the fixture's real admitted predecessor, carried history, held key and native transition sealer. Sign a fixture identity-key-state snapshot using `appendReceizIdentityPortableState` (schema `receiz.identity-key-state.v113`, synthetic Kai 150, `revokedAtKai:null`), native-seal and admit that exact identity under the fixture roots. Bind a diagnostic operation's `source` participant to `verifiedHistory.headDigests[0]`; prepare its execution-authority event with the SDK fixture's diagnostic request/outcome coordinates. Pass the actual admissions, exact plan/event, held key, Kai 150, expiry 200 and fixture sealer to the Wildz helper.

The returned member must have one exact `artifact.append` resource capability and `candidateIsCommitted:false`. Reopen the candidate under the same test roots, derive its actual carried proposed head, and inspect the resulting set through the SDK's package-internal `verifyReceizPortableExecutionTransitionSetWithVerifierContextV124`. Require `inspected-portable-execution-transition-set` and `candidateCustodyExposed:false`. Passing that same member to Wildz's production combine helper must reject it under pinned roots. Repeat with a changed expected source head and with a correctly signed fixture key state revoked at Kai 149; both must fail before the sealer is invoked. These three checks were executed successfully during this implementation. They verify preparation mechanics, not funded value or a committed trade.

## Requirements before implementation

1. A registered, qualified native reducer/source must consume exact predecessor value and subject/ownership heads and commit both parties' value and custody transitions in one supported execution domain or native aggregate. Resource package reservations and source custody must participate in the same atomic boundary.
2. Both peers must consent to the same frozen plan digest, exact assets, quantities, recipients, fees, expiry and expected heads. Autonomous execution needs bounded mandates covering that exact consideration and counterparties.
3. Stage the pinned-admitted candidate transitions without issuing an independently claimable gift. A rejection, stale head, expired consent or missing capability must produce zero writes across every participant, including ownership, one-use claims and resource reservations.
4. Persist semantic idempotency and recover one admitted aggregate outcome after lost responses. Cancellation before commit must release the entire aggregate; committed outcomes must have exact source receipts and no partial rollback fiction.
5. Only after that single admitted outcome may wallet/world/message projections show the exchanged assets. SDK, MCP and AI skills must call the same source executor and cannot become an alternative authority.

Acceptance evidence must include successful Φ + creature + resource exchange, either peer's failed consent, stale heads, replay/concurrent confirmation, expiry, cancellation, and lost-response recovery. Every rejected case must prove unchanged native balances and ownership, not only unchanged UI state. Until this support exists, report trading as unavailable and keep direct gifts clearly marked as awaiting recipient acceptance.

That original plan has now been implemented in source through additive v128 APIs; see [the implementation and rollout record](../../developers/native-wallet-rollout.md).
