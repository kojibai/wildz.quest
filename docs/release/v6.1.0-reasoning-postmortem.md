# v6.1.0 voice reasoning postmortem

The requirement was clear: use the neural speech capability already present in the Receiz v120 proof-subject/Twin system, make it creature-specific from deterministic proof characteristics, keep it off capture and gameplay hot paths, add no provider dependency, and stream text, audio, and mouth motion together.

The implementation reasoning deviated from that requirement. This postmortem records exactly how and turns the correction into a permanent engineering guardrail.

## What was reasoned incorrectly

### 1. A playback regression was misclassified as a missing synthesis system

The first wrong move was to see “the voice no longer plays” and jump to designing a new voice source. The correct first question was whether Wildz was consuming the v120 Twin performance events already available from the installed SDK and Receiz stream. The repository and installed `@receiz/sdk@120.0.0` explicitly expose subject performance, audio chunks, visemes, and reply completion.

This was an ownership-of-layer error: a broken adapter was treated as an absent platform capability.

### 2. Receiz SDK, MCP, and AI skills were conflated

The application already had the correct coordinated v120 toolchain. The SDK is the runtime contract. MCP is operator/conformance tooling. AI skills are implementation doctrine. Adding a separate provider route did not “use all three”; it bypassed their intended separation and duplicated a capability the Receiz performance rail already owned.

The correct interpretation of “use the SDK, MCP, and AI skills” is:

- build runtime behavior through the SDK;
- validate the release and inspect capabilities through MCP/conformance; and
- obey the proof, authority, performance, and failure laws in the AI skills.

It never means importing MCP into client code or choosing an unrelated provider because a tool package exists.

### 3. Provider-specific infrastructure was added without architectural necessity

The rejected design introduced a Wildz voice API key, a voice-session route, short-lived provider tokens, a direct browser WebSocket, provider voice IDs, and another failure/latency surface. Those pieces were unnecessary for the requested result and violated the zero-dependency constraint.

Even if secured correctly, unnecessary infrastructure is still wrong. It increases operational liability, configuration drift, billing exposure, failure modes, and the number of steps between reply and sound.

### 4. Deterministic character shaping was confused with speech generation

The proof-derived rate, pitch, brightness, gain, and mouth response are a small real-time presentation transform. They do not need their own model and must not become a substitute voice. The neural source remains Receiz v120; the proof transform only locks that performance to the exact creature.

The correct composition is:

```text
Receiz v120 neural performance + exact proof voice lock -> unique creature playback
```

It is not:

```text
generic browser/provider fallback + cosmetic parameters -> claimed neural creature voice
```

### 5. A fallback was treated as reliability

A local phrase generator or browser voice can make a demo appear responsive, but it destroys the product guarantee. If the contract says every accepted spoken reply is genuine v120 intelligence with the real unique voice, silently substituting another rail is not resilience; it is false success.

The corrected rule keeps the two projections separate: append a genuine Twin observation through the existing exact-head proof-memory path, and require the voice layer to use only the real v120 neural performance. Voice may never authorize, block, reorder, or erase proof memory.

### 6. The hot path contained repeated work

The card was verified/projected at request parsing, projected again in the route, projected again in the local subject adapter, and projected again in the client playback function. Those duplicates were individually defensible but collectively unnecessary.

The corrected implementation verifies once at the server entry boundary, reuses one exact server projection through v120 subject observation, and passes the already-memoized client projection directly to playback.

### 7. Latency language got ahead of evidence

A local function completing in a few milliseconds is not proof that audible neural speech completed in that time. Likewise, a 300 ms instrumentation target is not an end-to-end production guarantee. Claims must name their measurement boundary: first text delta to first audio scheduled, user gesture to sound, or full remote request. Production percentiles require authenticated production evidence.

## The correct decision process

For any future Receiz capability regression:

1. Read the installed package version and exact public API before designing a replacement.
2. Read the matching Receiz AI skill laws and application MCP contract.
3. Draw the existing authority and data path from verified artifact to UI projection.
4. Identify the broken adapter or unconsumed event.
5. Keep canonical truth, inference, performance, and presentation as separate layers.
6. Add only the smallest adapter required to consume the existing primitive.
7. Fail closed when a promised non-fallback output is absent.
8. Measure the real boundary before making a latency claim.
9. Add source tests that prohibit the rejected architecture, not only tests that permit the preferred one.

## Permanent guardrails

Future voice work must pass all of these checks:

- exact Receiz packages remain pinned to the coordinated release;
- the verified proof object remains strongest authority;
- the proof brain carries the stable voice signature and transform;
- one Receiz stream carries reply and performance;
- no Wildz provider key, session route, browser WebSocket, browser speech, or client model exists;
- text streams without waiting for final reply/audio;
- voice performance never gates or mutates the existing exact-head conversation-memory append;
- the mouth follows the actual waveform;
- capture, login, roaming, and render loops do not initialize or await voice;
- one request does not repeat exact proof verification/projection; and
- release notes separate source guarantees from production observations.

These are enforced by `pnpm receiz:architecture-lock`, which is mandatory inside `pnpm release:check`. The lock scans application runtime source, package pins, environment configuration, the observer route, proof-subject adapter, client playback, append ordering, and the checked-in doctrine. It fails the release if the rejected provider route/key/socket/model/fallback returns, if MCP or AI skills enter runtime code, if the official subject-performance SDK rail disappears, if the exact head/digest binding is removed, or if voice is allowed to gate proof-memory append.

The mistake was not that the requirement was impossible or ambiguous. The mistake was failing to begin from the installed Receiz v120 primitive and its documented layer boundaries. `v6.1.0` corrects the code and records that reasoning failure so a future engineer has both the required architecture and the rejected alternatives in one place.
