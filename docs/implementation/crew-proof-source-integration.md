# Crew proof source integration

The crew source/mandate adapters verify exact carried artifacts through installed SDK v126. They do not establish a working autonomous crew or global currentness. No live mandate was issued while implementing them.

`src/lib/receiz/wilds-crew-source-authority.ts` uses `openReceizSubjectSourceFamilyV125`, `readReceizSubjectSourceFamilyMemberV125`, and `readReceizTemporalSubjectSourceV125`. The source family opener canonically verifies exact bytes, PBI predecessor chains and subject lineage. The crew adapter derives owner and worker IDs, ownership and subject heads from sealed sources. It separately retains the temporal proof head for SDK PBI confirmation verification; that head is not interchangeable with the subject execution head. Identity signatures must bind the exact confirmation digest and verify against both source chains. Runtime admission still needs atomic current subject-head, owner, expiry, consent and revocation checks.

`src/lib/receiz/wilds-crew-mandate-authority.ts` calls `client.subjectMandates.issue`, `.state`, and `.revoke`. Issue requires the prepared exact mandate and signed confirmation; revocation signs its own exact request. Append fields are explicit admission inputs, not fabricated by this adapter. Responses are labeled unverified transport/index data and cannot authorize execution. After an uncertain mutation response the adapter reports unknown writes and required recovery; it does not replay the mutation.

## Existing bytes and the missing bridge

Existing cards can produce real primary sealed bytes. `prepareWildzIdentityOwnedCard` in `src/lib/receiz/wildz-identity-adapter.ts` builds a portable card PNG, embeds an Identity-bound player vault, calls `createReceizProofObjectArtifact`, and returns exact artifact bytes. `downloadWildzIdentityPlayerVault` similarly exports a sealed vault. This is an application integration gap, not absence of an SDK service or an inability to seal cards.

The V125 source family additionally requires the exact Identity source, complete PBI predecessor artifact bytes and a sealed temporal subject source. `sourceFamilies.create` only packages artifacts; it does not seal, admit, reconstruct or grant authority. `sourceFamilies.open` requires actual carried `pbiAuthorshipHistory` and all referenced predecessors. Its temporal subject reader requires an admitted single-head portable proof history with verified KKS data.

Current `projectWildsCreatureSubjectAdmissionV122` in `src/lib/receiz/wilds-v122-subjects.ts` serializes the application `PortableCardAsset` as JSON. That projection is not the sealed PNG from the export pipeline. Existing `prepareWildsLivingWorldAuthoritySession` in `src/lib/receiz/wilds-living-world-authority.ts` constructs a V124 source candidate from a subject-state response and a single provenance marker. It does not carry the complete temporal/PBI family required by the V125 reader.

The installed authenticated `client.subjects.exportEdgeBundle(subjectId, verifier)` calls `/api/sdk/v1/subjects/:id/export`. It retrieves exact primary bytes plus append segments but requires application admission, owner, append and registry/reducer verification callbacks. It does not produce a V125 temporal source family. `subjects.resolve` returns legacy subject artifact JSON; `subjects.history` returns event records; `subjectCoordination.readTemporalSource` is a local reader. `client.sources` exposes sealed-source publication, not a subject-family resolver. Replacing missing proof evidence with callback success would introduce false authority.

## Exact source retention wired to production exports

`createWildzProofSourceRepository` now retains SDK-verified exact sealed artifacts under content-addressed keys in the existing IndexedDB `artifacts` store. It never replaces or removes predecessors. `prepareWildzIdentityOwnedCard` retains the actual sealed export before returning the prepared card and appends its digest to an asset-location index. `downloadWildzIdentityPlayerVault` retains the verified export before saving it to the device. Index entries are candidate locations, not subject identity or ownership, and every historical export remains available.

The repository reads existing `WildzArtifactHistoryEntry` objects directly, so restored admitted sources from the codec's existing artifact opener are reusable without another stored Base64 copy. Canonical SDK verification runs again on retrieval; claimed row metadata cannot establish authority. Family retrieval accepts exact binding selections, follows every carried PBI predecessor reference, reports exact missing hashes and then invokes the SDK family creator/opener. It yields between groups of eight retrieved sources without truncating history. This work runs on export/explicit retrieval, never in an animation loop.

Identity-only PNGs in the existing application carry Identity key-file trailers and are handled by the encrypted identity repository. They are not presumed to be the canonical sealed Identity source needed by `sourceFamilies.open`, and this change does not copy plaintext key carriers into the proof-source store.

Remaining activation gap: the current application creature record does not carry a verified binding between its existing subject identity/history and its newly sealed PNG export. Automatically admitting each export would derive a new digest-based subject ID and could fork an existing creature's history. Crew activation must resolve that actual existing-subject binding, retrieve the sealed Identity/PBI predecessors and temporal subject source, and verify them before using `subjects.admit` for a genuinely absent subject. The source repository supplies exact retained primary bytes now; it does not synthesize the missing temporal/PBI evidence or reissue an old creature as genesis.

Focused retention/history tests: 12 pass. Tests cover zero writes for unsealed input, missing exact predecessor reporting, canonical revalidation of restored rows, corrupt source rejection, coexistence with legacy history, legacy history preservation. No positive complete-family fixture or live autonomous execution was produced.

Asset source locations use immutable per-asset digest entries linked to their predecessor and a constant-size head pointer. Each export performs a bounded number of index reads/writes; `locateAsset` retrieves 24 entries by default (maximum 96) with an explicit continuation cursor. Canonical artifact history remains complete. Family collection follows SDK role semantics: recursively include predecessors of current selected PBI sources, while Identity and temporal subject selections are exact independently opened roles. The SDK rejects arbitrary extra/unselected family artifacts.

Family opening has a hard work limit of 256 distinct sources and 64 MiB aggregate decoded primary bytes; callers may request smaller limits. Root binding count is also bounded before cloning or reading. Byte budget is charged before base64 decode/canonical verification for retained sources and before verification for legacy sources. Revisited sources reuse canonical results and are charged once. Exhaustion reports an explicit error without deleting, rewriting or truncating retained history; it does not return a partial family.

## Existing subject identity and replay follow-up

Read-only SDK inspection confirms `prepareReceizSubjectSourceProofObjectCandidateV124` preserves the supplied subject ID, proof-object ID and execution head. A source carrier can therefore preserve identity without readmitting each export. However, sealing a row-derived carrier does not provide the original artifact or complete temporal history.

The public `client.domains.verifiedReplayV124` → `exportVerifiedReplayProofObjectV124` → `client.assets.createProofObject` → `restoreVerifiedReplayProofObjectV124` path preserves canonically admitted domain replay custody. Its carrier is a domain replay source, not a temporal subject source; these types are not interchangeable. Exact-KKS append also requires a verified KKS predecessor (`ARTIFACT_APPEND_PREDECESSOR_KKS_REQUIRED` when absent), and initial temporal issuance cannot migrate an existing history. Collecting the original primary source and actual verified replay lineage remains necessary before enabling worker authority. No missing history has been manufactured and no former identity has been replaced.

The SDK also exposes `client.coordination.remoteDomain({ namespace, commitDomain }).resolveAcceptedHead({ artifactId, knownHead })`. For an already registered portable source this resolves exact bytes and admitted history through the SDK verifier. The current card record does not contain those registered temporal/Identity artifact coordinates; an export hash or subject execution ID is not a substitute. Activation must obtain the actual registered artifact ID, namespace and commit domain from verified source evidence before using this recovery route. No unused recovery helper or guessed coordinate was introduced.
