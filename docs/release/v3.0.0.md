# Wildz v3.0.0 — first public open-source release

Wildz v3.0.0 is the first public release of a real product built by forking the open-source [Receiz Commerce Kit](https://github.com/kojibai/Receiz-commerce) and driving its proof-native application model into a new category: a persistent, portable, game-first world.

The point of this release is not that an SDK can complete a checkout. It is that one coherent set of identity, proof, custody, publication, ownership, settlement, MCP, and AI-operating primitives can support an entire product: player genesis, living artifacts, deterministic game systems, social presence, public identity, multiplayer, offline continuity, and a market—without quietly promoting a database, cache, agent, or payment response into authority.

Version `3.0.0` is both the current product version and the first public open-source release. The name reflects the third major Wildz product architecture, not three prior public releases.

## What is remarkable about this release

### A reference implementation that is also the product

Wildz is not a detached example directory. The same application people play at [wildz.quest](https://wildz.quest) is the implementation developers can inspect, run, test, and extend. The repository contains the product UI, deterministic game kernels, Receiz integration boundary, public APIs, PWA behavior, operator tooling, AI skills, and release evidence as one reviewable system.

### An architectural fork, not a reskin

Receiz Commerce Kit begins as a commerce cloud and forkable SDK kernel. Wildz removes the merchant admin, CMS, and storefront navigation and constructs a different vertical product:

- Customers become explorers with portable identity and owner-scoped continuity.
- Receized assets become living creature cards used directly in deterministic play.
- Storefront public state becomes a world, profile, and public-card projection.
- Commerce events become world, battle, social, market, and settlement commands.
- Operator tooling becomes a proof-aware AI build, market, and release layer.

The fork demonstrates which parts of a Receiz application are true reusable infrastructure and which parts belong to the product.

### AI operates; proof decides

The repository ships with Receiz MCP integration and three checked-in Wildz AI skills. An agent can inspect capabilities, follow exact build doctrine, prepare market operations, and execute release checks. It cannot bypass artifact verification, actor binding, ownership heads, settlement admission, player confirmation, or release authority.

This is the intended end-to-end model for agent-native software: make the system highly operable by AI while keeping truth, permission, and irreversible outcomes independently verifiable.

## Receiz v114 implementation

`receiz.app.json` declares `identity`, `proof`, `proofMemory`, `publicStore`, and `commerce` with artifact-first authority and `allowDatabaseAuthority: false`. The official compiler produces the deterministic evidence in `receiz.generated.json`.

`pnpm receiz:check` validates the target release, ruleset, registry digest, 16-operation matrix, limits, authority flags, numbered artifact laws `ARTIFACT-001` through `ARTIFACT-030`, and v114 showcase authority. Checker success means the repository contains the declared integration evidence. It is not artifact truth, live capability evidence, or proof that a remote mutation occurred.

The v114 transition model implemented and tested here requires:

1. Exact artifact bytes cross the verifier.
2. Admission determines eligibility but grants no mutation authority.
3. Planning is zero-write and binds current verified history, actor, registry law, canonical event, expected head, idempotency, and commit domain.
4. Only a verified, plan-bound capability may seal the candidate.
5. Staging is immutable and does not advance the accepted head.
6. Commit independently resolves and reverifies staged bytes before an atomic head advance in the named domain.
7. Receipts report what happened and cannot re-enter an authority-bearing API.

V114 adds zero-write planning for profile-showcase genesis/append and economy-showcase genesis/append/merge. Profile identity is the literal `profile-showcase:<owner>`, never a payload digest; successor history travels in the sealed bytes without introducing a new signer, issuer, or head authority. Economy merge planning additionally requires verified sibling heads.

Global resolution uses `receiz.com/global/v1` as a named coordination domain. “Global” does not mean universal consensus. Known verified artifact truth paints before remote startup, returned bytes are independently verified, structural divergence is preserved, and effect-delivery status remains distinct from accepted-head status. A queued proposal is not a global commitment.

- `receiz_artifact_admit`
- `receiz_artifact_append_plan`

- `receiz_artifact_global_resolve`
- `receiz_artifact_reconcile_plan`

The Wildz builder, market-operator, and release skills bind agent work to the same custody, authority, confirmation, and qualification rules as application code. Credentials and passphrases must never enter prompts, logs, examples, browser storage, generated proof metadata, or MCP resources.

## Security and integrity improvements

- Complete-artifact verification is the only gateway to artifact payload parsing.
- Native proof creation binds authenticated owner, record, claim, verify path, Signature V4, artifact/payload digests, and exact-file reopen.
- Verification and materialization obey published v114 resource limits.
- IndexedDB records are owner-scoped; immutable digest history cannot be overwritten with conflicting bytes or provenance.
- Historical creator/owner coordinates remain provenance and are not rewritten during cross-application restore.
- Legacy runtime authority objects cannot authorize the current v114 receiver.
- Public caches allow only explicitly sanitized, successful, exact-URL responses.
- Security response headers include CSP, frame denial, no-referrer, denied browser permissions, and same-origin opener isolation.
- A full tracked/untracked text secret scan is part of the release gate.

## Installation

```bash
git clone https://github.com/kojibai/wildz.quest.git
cd wildz.quest
corepack enable
pnpm install --frozen-lockfile
cp .env.example .env.local
pnpm dev
```

The app can boot locally with empty production credentials. Review `.env.example` before enabling any live rail. Never put server credentials behind a `NEXT_PUBLIC_` prefix.

## Known limitations and pending external gates

This release does not turn unavailable production evidence into a marketing claim:

- Authorized `pnpm receiz:doctor:strict` qualification remains pending until production configuration is supplied.
- Remote world, profile, market, payment, transfer, settlement, and publication mutation qualification remains pending.
- The required Wildz conditional market-ownership append is absent from the v114 SDK, so affected live mutations fail closed.
- The external six-writer artifact exercise remains pending; local six-writer fixtures pass.
- Deployment, Git tag, push, GitHub Release publication, and production announcement are not performed by the local release gate.

There is no external database added by Wildz. Durable shared world, public, social, and economy state requires configured Receiz rails. A checkout session is not settlement, a plan is not a write, a receipt is not reusable authority, and a queued proposal is not a global commitment.

## Compatibility

- Current execution and qualification are v114-only.
- Historical sealed bytes remain eligible for current verification.
- Verified legacy v102 portable assets are read-compatible through the bounded compatibility path.
- Historical runtime admissions, actors, plans, capabilities, stores, confirmations, and receipts cannot authorize a current receiver.
- The historical forward-only migration checkpoint remains compatibility evidence; no sealed artifact, receipt, or accepted head is rewritten.

## Upgrade notes

This is the first public release, so there is no public upgrade path from an earlier tag. Existing private or development deployments should:

1. Use Node.js `20.18.0` or newer and pnpm `10.29.1`.
2. Install with the frozen lockfile and verify all Receiz packages resolve to `114.0.0`.
3. Compare environment configuration with `.env.example`; do not reuse player tokens as Connect or release credentials.
4. Preserve all sealed artifacts, receipts, accepted heads, and migration checkpoints.
5. Run `pnpm release:check` before deployment.
6. Run the authorized strict-live doctor in the target environment.
7. Complete external interoperability and remote mutation qualification before representing those capabilities as live.
8. Bump `NEXT_PUBLIC_WILDZ_SW_RELEASE` for each production worker release.
