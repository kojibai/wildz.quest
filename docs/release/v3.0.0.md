# Wildz v3.0.0

Wildz v3 is the standalone world, living-card collection, identity, social, and market PWA release candidate. The package is versioned `3.0.0`, and the exact local candidate has passed its repository release gate.

## Receiz v104 toolchain

- `@receiz/sdk 104.0.0` is pinned exactly for application identity, artifact, native proof-object, App Contract Compiler, checker, and rail integration.
- `@receiz/mcp-server 104.0.0` is pinned exactly for operator tooling.
- `@receiz/ai-skills 104.0.0` is pinned exactly for v104 operator procedures.

The official v104 SDK and MCP release tarballs, plus their matching AI-skills artifact, are vendored and lockfile-pinned until registry publication. Vendoring changes only the package source; it does not fork, patch, or replace SDK proof logic.

MCP and AI skills do not outrank SDK verification, proof-object continuity, ownership heads, settlement admission, or player confirmation. Their installation does not prove that they were invoked during release qualification.

`receiz.app.json` declares the v104 Wildz contract with `identity`, `proof`, `proofMemory`, `publicStore`, and `commerce`, artifact-first authority, and database authority disabled. The official compiler produces the deterministic plan represented by `receiz.generated.json`. `pnpm receiz:check` runs the v104 repository checker and participates in `pnpm release:check`; it validates repository evidence for authenticated Record before Seal, durable proof memory, continuity, idempotency, and browser-safe secret handling. Compiler/checker success is not strict-live or remote-mutation evidence.

## V3 highlights

- Owner-scoped continuity covers the player’s cards, support selection, settings, history, receipts, and canonical world cursor.
- Identity Seal and verified identity-bearing Vault flows activate the embedded Receiz identity; a card-only Vault can add verified cards but cannot invent identity authority.
- The world model includes ecology, settlements, social memory, raids, bosses, mastery, routes, and canonical event projections.
- Public profiles and public cards use sanitized canonical routes and durable Receiz projection contracts.
- Listings, offers, trades, checkout, and transfers require current ownership, expected revision, idempotency, actor authority, and verified Receiz admission.
- The v104 SDK does not expose the Wildz-specific conditional market ownership append; those mutations fail closed as unavailable until that verified capability exists.
- Checkout creates no synthetic ownership: a settled result requires a Receiz Connect transfer proof, the matching wallet-ledger event, and a conditional market ownership append; retries reuse the same transfer key.
- New exports use the v104 native Record → Seal flow and download the SDK-returned artifact byte-for-byte. The deployed `wildz-v103` idempotency namespace remains stable across the SDK upgrade. Existing v102 portable proof objects remain read-only compatible through Wildz's strict app-owned compatibility reader.
- The installable PWA uses release-distinct caches, explicit install/update consent, a state-preserving update transition, and security response headers.

## Identity and proof authority

Receiz proof and Identity Seal verification are authoritative. Wildz admits an identity-bearing artifact only after its identity binding and required proof are verified. New proof creation accepts only SDK v104 native continuity whose owner, claim, verify path, bundle verification, and final artifact agree. Legacy portable objects additionally retain their bound payload, namespace, and prior-head checks. Stale, conflicting, malformed, or unverifiable material fails closed.

The enclosing verified player Vault establishes the current identity and custody. Historical owner coordinates inside cards remain immutable provenance; they do not prevent a compatible cross-platform Vault from restoring the complete collection. Exact duplicate cards are dropped, a strictly verified newer revision wins, and divergent same-ID proof forks fail.

Local IndexedDB preserves owner-scoped state for the installed experience, but it does not replace remote proof, publication, market, or settlement authority.

## Exact offline boundary

Previously visited public profiles, previously visited public cards, and cached card details may remain readable. The versioned app shell can start without a network connection and owner-scoped verified local state may still be present on the device.

Sign-in, the live world, social presence, the market, publishing, listing, trade, transfer, and payment require a connection. Authentication, world, market, Receiz, artifact-proxy, and mutation traffic is not cached. An unvisited public page receives the offline guidance page rather than another player’s or the root document. This boundary does not claim that the live game or mutations work offline.

## Remote capability boundary

There is no external database added by this release. Durable shared world, profile, social, and economy state is admitted through configured Receiz rails. Durable Receiz rails fail closed when unavailable, stale, or unverifiable; no fallback reports a remote mutation as successful. A checkout session is not settlement, and ownership does not transfer before settlement admission.

## Qualification status

The exact local candidate passed `pnpm release:check`: the v104 application-contract checker, complete Node test suite, typecheck, lint, the full tracked/untracked text secret scan, the production build, and the default Receiz doctor. Chromium and WebKit mobile entry checks passed; Chromium also passed the real service-worker/offline rehearsal. The supplied production-shaped Vault decoded to 98 cards plus an embedded player and restored all of them through the browser path with a mocked successful verifier. That result does not claim live Receiz verification.

The strict-live doctor was attempted and failed closed before live probes because production configuration was absent. Authorized strict-live verification, remote mutation, the external six-writer exercise, deployment, tag, push, and production publication remain pending. The local candidate is ready to commit; production activation remains conditional on those external gates.
