# Crew proof source integration

The crew source/mandate adapters verify exact carried artifacts through installed SDK v126. They do not establish a working autonomous crew or global currentness. No live mandate was issued while implementing them.

`src/lib/receiz/wilds-crew-source-authority.ts` uses `openReceizSubjectSourceFamilyV125`, `readReceizSubjectSourceFamilyMemberV125`, and `readReceizTemporalSubjectSourceV125`. The source family opener canonically verifies exact bytes, PBI predecessor chains and subject lineage. The crew adapter derives owner and worker IDs, ownership and subject heads from sealed sources. It separately retains the temporal proof head for SDK PBI confirmation verification; that head is not interchangeable with the subject execution head. Identity signatures must bind the exact confirmation digest and verify against both source chains. Runtime admission still needs atomic current subject-head, owner, expiry, consent and revocation checks.

`src/lib/receiz/wilds-crew-mandate-authority.ts` calls `client.subjectMandates.issue`, `.state`, and `.revoke`. Issue requires the prepared exact mandate and signed confirmation; revocation signs its own exact request. Append fields are explicit admission inputs, not fabricated by this adapter. Responses are labeled unverified transport/index data and cannot authorize execution. After an uncertain mutation response the adapter reports unknown writes and required recovery; it does not replay the mutation.

## Existing bytes and the missing bridge

Existing cards can produce real primary sealed bytes. `prepareWildzIdentityOwnedCard` in `src/lib/receiz/wildz-identity-adapter.ts` builds a portable card PNG, embeds an Identity-bound player vault, calls `createReceizProofObjectArtifact`, and returns exact artifact bytes. `downloadWildzIdentityPlayerVault` similarly exports a sealed vault. This is an application integration gap, not absence of an SDK service or an inability to seal cards.

The V125 source family additionally requires the exact Identity source, complete PBI predecessor artifact bytes and a sealed temporal subject source. `sourceFamilies.create` only packages artifacts; it does not seal, admit, reconstruct or grant authority. `sourceFamilies.open` requires actual carried `pbiAuthorshipHistory` and all referenced predecessors. Its temporal subject reader requires an admitted single-head portable proof history with verified KKS data.

Current `projectWildsCreatureSubjectAdmissionV122` in `src/lib/receiz/wilds-v122-subjects.ts` serializes the application `PortableCardAsset` as JSON. That projection is not the sealed PNG from the export pipeline. Existing `prepareWildsLivingWorldAuthoritySession` in `src/lib/receiz/wilds-living-world-authority.ts` constructs a V124 source candidate from a subject-state response and a single provenance marker. It does not carry the complete temporal/PBI family required by the V125 reader.

The installed authenticated `client.subjects.exportEdgeBundle(subjectId, verifier)` calls `/api/sdk/v1/subjects/:id/export`. It retrieves exact primary bytes plus append segments but requires application admission, owner, append and registry/reducer verification callbacks. It does not produce a V125 temporal source family. `subjects.resolve` returns legacy subject artifact JSON; `subjects.history` returns event records; `subjectCoordination.readTemporalSource` is a local reader. `client.sources` exposes sealed-source publication, not a subject-family resolver. Replacing missing proof evidence with callback success would introduce false authority.

## Smallest next integration

Retain the exact output of `prepareWildzIdentityOwnedCard` together with the restored Identity source and every PBI predecessor artifact in the existing proof-object repository, keyed by actual artifact SHA-256. Admit that exact primary object through `client.subjects.admit`; do not derive its ID from projected card JSON. For a genuinely new subject only, use `client.subjectCoordination.prepareInitialTemporalSource` with its actual initial subject admission, admitted KKS coordinate and empty genesis history, seal its returned proof object with `client.assets.createProofObject`, then canonically read and retain the result. That initializer explicitly rejects existing histories and must not be used to relabel an existing creature as genesis.

Existing subjects require preservation and verified replay of their actual carried history before a temporal source is sealed. Retain every resulting source and predecessor; assemble with `client.subjectCoordination.sourceFamilies.create` and open it before preparing the crew policy. The UI can consume this retained source set without asking the owner to manually upload a family. Until those sources are available and verified, the assignment remains a proposal. Global currentness and cross-device admission remain separate required runtime checks.

Validation: focused adapter tests cover state-as-index handling, rejection of empty/forged families and zero dispatch on malformed issue/revoke requests. There is no positive real primary-source fixture or live issuance/admission evidence yet; these tests do not establish end-to-end readiness.
