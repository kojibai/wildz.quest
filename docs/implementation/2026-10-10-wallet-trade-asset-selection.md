# Wallet trade asset selection

The trade builder must expose every currently transferable asset without a presentation cutoff. Its offered package groups the existing holdings as food, materials, creatures and resource packages, offers name search and shows each selected quantity. Filtering must retain the original selection IDs, available quantities and exact source IDs used by the existing draft and staged exchange adapters. Search reads display labels only; it never serializes or inspects proof bodies.

The requested package is a descriptive wishlist built from the same familiar local names. It carries selected names and quantities through the existing `requestNote` field, identifies that the peer supplies the exact items in a counteroffer, and grants no custody or ownership. Duplicate local display names collapse in the wishlist, while distinct offered source lots stay separate. PHI, review, saved recovery, approval, native sends and peer counteroffer authority stay on the existing paths.

Inspection used the repository's `@receiz/sdk@128.0.0` README and function/client inventory, the connected read-only `receiz_capabilities` describe output and the installed v128 AI performance and bearer ownership instructions. Their boundary is preserved: sealed source and carried ownership remain above UI projections. This change performs no Receiz command, proof verification, signing, enrollment, claim or transfer through MCP. No new capability or authority adapter is required.

Validation covers a 68-creature inventory with food and material holdings, category/name/selected filtering, exact offered food and material IDs, and wishlist quantity formatting. Desktop and mobile browser integration should exercise independent offered/requested filtering, a selected item retained while a different category is shown, quantity editing, review and edit, and the existing inbox/approval/send paths. The selector list and selected summary have bounded scrolling so the review action remains reachable on a narrow screen.

The new rendered component tests first failed against the original builder because Creature 68 and requested selector controls were absent. An isolated TypeScript test build then passed all 40 trade tests, including five selection regressions, and focused ESLint checks passed. The parent implementation task owns the shared full-suite and browser runtime checks.
