## Why explicit world-rule dispatch preserves the existing source

`WILDS_RESOURCE_LAW_V128.birth` is `full-genesis-command-replay`; its finite
source contract is `global-current-head-and-exact-command`. The law delegates
resource outcomes to deterministic typed world replay. It does not contain a
frozen list of construction rule heads. The resource reducer computes its
coordinates from that law and the literal reducer revision `:4`.

At the base commit, `creation/world-source.ts` already selected distinct
`creation.world.construct.v1`, physical `construct.v2`, `evolve.v1`, physical
`evolve.v2`, and gear v2 rule heads. Commands bind their definition, context and
plan digest; `creationWorldBuildRuleHead` selects an explicit rule; admitted
creation records carry `ruleHead`; `compileWorldCreationSource` rechecks it.
`replayWildsResourceGameplayV128` already admits typed `creation.construct`,
`creation.evolve` and `creation.action` through `WildsWorldService.execute`.
`reduceWildsResourceJournalV128` already rejects changed owner-trace prefixes
and compares unseen source advances with global frontiers.

Therefore a marker-selected new world rule is an extension at this existing
versioned delegate boundary. It must not change the behavior of marker-absent
commands, reassign an existing world rule head, or treat a construction mesh as
resource authority. The marker and new rule digest must commit the complete
clearance consequence, including retirement, finite remaining contents,
original source heads, paid building identity and side locations. The current
uncommitted terrain v2 marker by itself does not implement that consequence.

This judgment is grounded in the existing delegate contract and multi-rule
implementation; the SDK does not inspect or approve Wildz game semantics.
Successful preparation of opaque event bytes does not validate a clearance.
The new application rule still needs its mandatory semantic qualification.

## Why a new source or renamed digest is not a shortcut

The released segment verifier checks equal predecessor application, domain,
registry, reducer, genesis/proof-object identity, cursor and causal head.
`prepareReceizDomainReplaySegmentProofObjectCandidateV124` independently opens
its predecessor with the requested registry/reducer. Renaming the source
registry/reducer cannot continue the old replay chain silently.

The custom atomic planner binds `custom:` namespaces to explicit source
registry/reducer digests. Its registered operation schema is not a source
retirement command. Two custom operations in different domains are rejected
with `V124_ATOMIC_CROSS_DOMAIN_UNSUPPORTED`; its special multi-domain support
requires verified world-transaction forms. Planning a custom participant with
a digest-shaped expected head does not enroll or retire an existing source
publication head. The qualification asserts these real SDK checks.

No native capability gap is claimed. There is no substitute source, database,
authority callback, SDK core change or unqualified handoff in this task.
